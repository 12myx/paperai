# 03 · 赛题材料生成提示词

> 这些提示词用于让码道生成**材料内容**，你负责真实截图、排版、录制和最终提交。
> 每个提示词都可以直接粘贴；生成后请按赛题目录归档。

---

## 1. 作品说明文档（`readme/`）

### 提示词

```text
请为 PaperLens AI 撰写《作品说明文档》，中文，Markdown，面向大赛评委。必须严格覆盖赛题要求的四部分，并额外包含“可复现验证”。

结构：
1. 作品概览：一句话定位、目标用户、解决的真实问题、与通用 PDF 聊天工具的区别。
2. 环境依赖说明与一键安装脚本：
   - 操作系统、Python 3.12、Node.js 20+、Docker（可选）
   - 依赖清单与版本
   - Windows / macOS / Linux 命令
   - 一键脚本 scripts/setup.ps1 与 scripts/setup.sh 的用途与执行方式
3. 部署运行步骤：
   - 本地开发（后端 + 前端）
   - 生产构建（FastAPI 托管 dist）
   - Docker Compose
   - 环境变量表（SECRET_KEY、DATABASE_URL、STORAGE_DIR、DEEPSEEK_API_KEY、CORS）
   - 健康检查与首次使用
   - 常见问题（上传 413、PDF 解析失败、翻译 409、SSE 不流式、端口占用）
4. 额外使用的开源组件说明：
   - FastAPI、SQLAlchemy、PyMuPDF、pdf.js、React、Vite、ReportLab、python-docx、KaTeX 等
   - 每个组件的作用、License（如 MIT/BSD/Apache-2.0/AGPL 需注明）、是否修改
   - 明确没有使用盗版/未授权素材
5. 码道在项目开发中的应用总结：
   - 覆盖阶段：环境搭建、后端、前端、调试、测试、文档
   - 典型 Prompt 与产出（不要编造，留占位符由我填真实截图编号）
   - 效率提升与人工复核
   - 真实不足：哪些地方 CodeArts 生成后需要手改
6. 可复现验证清单：从零到跑通的命令与预期结果；测试命令与通过标准。
7. 能力边界：无 Key 的本地抽取模式、扫描版 PDF 需要 OCR、检索为词法混合、不支持图片视觉输入。

要求：
- 面向“评委能照文档复现”的目标写，不要营销空话。
- 命令必须能在 Windows PowerShell 与 Linux 下执行。
- 不要写未实现的华为云服务；没有接入就写“预留适配”。
- 需要我填真实数据的地方用【待填：xxx】标注，不要编造测试数字。
```

## 2. PPT / PDF 内容（`ppt/`）

### 提示词

```text
请为 PaperLens AI 生成一份 14 页的参赛 PPT 文案（中文），每页给出：标题、3-5 条要点、演讲者备注（40-80 字）、建议配图/截图。面向区域赛评委，对齐评分维度：功能完备 30、码道深度 25、专业贴合与创新 25、技术架构 15、交付规范 5。

页面结构：
1. 封面：PaperLens 知研 · 可追溯的 AI 科研智能体；队伍/学校/版本。
2. 场景与痛点：研究生每周读 5-15 篇论文；摘要不可追溯；结论留不住；多论文难对比。
3. 解决方案：一条研究链路（上传→解析→阅读→引用问答→对比→知识→项目）。
4. 产品演示总览：四个核心界面截图（首页/阅读器/多论文/知识库）。
5. 核心功能 1：可追溯问答——[C1] 引用、页码、原文片段、点击回跳。
6. 核心功能 2：智能阅读——章节、图表、5 色高亮、笔记、翻译、批判性评估。
7. 核心功能 3：多论文研究——综合对比、自选片段对比、研究缺口。
8. 核心功能 4：长期知识资产——知识库、图谱、项目、6 种导出。
9. 技术架构：React/FastAPI/SQLite/Postgres/pdf.js/PyMuPDF/DeepSeek；分层图。
10. 工程质量：26 个后端测试、21 步浏览器验收、Docker、备份、安全隔离；给数据但要真实。
11. 码道深度使用：环境搭建/代码生成/排错/测试/文档五阶段；Prompt 设计方法；证据索引。
12. 差异化与创新：证据契约、诚实降级、写操作确认、片段对比、提示注入防护。
13. 落地与价值：高校科研/毕业设计/实验室组会；可扩展到 OPC 与团队版；成本与部署方式。
14. 总结与展望：OCR、向量检索、团队协作、华为云 OBS；答辩致谢。

要求：
- 每页文字不要超过 60 字（除备注）。
- 明确标出哪些数据需要我用真实截图/测试结果替换，用【待填】标注。
- 不要编造用户量、收入、合作单位。
```

## 3. 功能演示视频脚本（`video/`，≤3 分钟）

### 提示词

```text
请为 PaperLens 写一份 3 分钟功能演示视频脚本，包含：时间轴、画面操作、旁白、字幕要点、要突出的评分点。

时间分配：
0:00-0:15 开场：产品名 + 一句话价值 + 目标用户。
0:15-0:40 登录 + 首页：研究范围、模式、资料库规模。
0:40-1:20 核心：上传/打开论文 → 提问“这篇论文的方法在哪些数据集上验证过？” → 展示流式回答、[C1] 引用、点击引用回到 PDF 页码。
1:20-1:50 阅读器：选中一段文字 → 黄色高亮 → 写笔记 → 刷新页面证明高亮恢复；展示批判性评估。
1:50-2:20 多论文：选择 2 篇 → 对比 → 来源卡片；自选片段对比。
2:20-2:40 知识库/项目/导出：保存结论到知识库、查看图谱、导出 DOCX 并打开。
2:40-2:55 码道应用：快速展示 IDE 中的 Prompt 与生成记录（真实截图），说明全流程使用。
2:55-3:00 收尾：能力边界与展望。

要求：
- 旁白口语化，不要念功能清单。
- 每个操作给出具体点击位置（按钮文案）。
- 标注“此处停顿 1 秒让评委看清引用”。
- 不要出现 API Key、个人邮箱、真实姓名。
- 给出录制建议：1920×1080、浏览器 100% 缩放、关闭通知、提前准备演示数据。
```

## 4. 码道使用证明包（`codearts_proof/`）

### 提示词

```text
请为 PaperLens 设计“华为云码道使用证明”材料包的结构与说明文档。注意：我不能伪造记录，你只生成模板、目录规范、截图清单和说明文字，真实截图由我补。

请输出：
1. 目录结构：
   codearts_proof/
   ├── 01_环境搭建/
   ├── 02_代码生成/
   ├── 03_调试排错/
   ├── 04_测试验收/
   ├── 05_文档与材料/
   ├── prompt_log.md
   └── README.md
2. 每个目录应放的截图清单（至少 5 类）：
   - 环境搭建：码道插件安装、项目初始化、依赖安装、首次运行
   - 代码生成：核心模块 Prompt、生成结果、文件树/diff
   - 调试排错：报错截图 + 定位 + 修复后通过
   - 测试验收：pytest 通过、浏览器验收、移动端
   - 文档材料：README/PPT/视频脚本由码道辅助生成
3. README.md 模板：项目背景、码道使用时间线、五阶段说明、证据索引表（编号/文件/说明/日期）、真实性声明。
4. prompt_log.md 模板：阶段、目标、Prompt 摘要、产出文件、验证结果、截图编号。
5. 截图规范：包含 IDE 窗口、Prompt、生成结果、时间；文件名 phase01_env_01.png；不要裁剪掉关键信息；敏感信息打码。
6. 一段 150 字的“码道应用总结”，可直接放进作品说明文档。

不要生成假的日期、假的截图内容或虚构对话；所有【】占位符由我替换为真实记录。
```

## 5. 答辩 Q&A（手动演练用）

### 提示词

```text
请为 PaperLens 生成区域赛答辩 Q&A，15 个问题，每个回答 80-150 字，基于真实实现，不夸大。

覆盖：
1. 为什么做这个作品？和 ChatGPT/通用 PDF 工具有什么不同？
2. 引用是怎么做到可追溯的？切片如何保存页码和坐标？
3. 没有模型 Key 时怎么工作？会不会是假 AI？
4. 多论文对比如何避免编造？
5. 研究缺口分析的依据是什么？如何避免“几篇论文代表整个领域”？
6. 如何保证用户论文隐私与数据隔离？
7. 提示注入怎么防？
8. 技术架构为什么选 FastAPI + React + SQLite/Postgres？
9. 检索为什么用 BM25 + n-gram，不上向量库？
10. 大 PDF/并发上传怎么办？当前限制是什么？
11. 码道在项目中具体做了什么？举 2 个真实例子。
12. 哪些代码是码道生成后你手改的？为什么？
13. 作品最大的创新点是什么？一句话。
14. 商业化/落地路径是什么？高校之外还能用在哪？
15. 下一步最想做什么？OCR、向量检索还是团队协作？

要求：回答要有“边界感”，主动说局限；不要承诺未实现的功能。
```

## 6. 对照评分表自检

### 提示词

```text
请作为区域赛评委，按以下 100 分评分表给 PaperLens 打分，并给出扣分点与 3 天内可完成的改进建议。不要客气，不要给虚高分数。

评分表：
- 功能完备度 30：核心功能完成度、逻辑顺畅、UI/UX 专业度
- 码道深度使用 25：全流程覆盖、Prompt 质量、证据完整真实
- 专业贴合与创新 25：专业需求、落地合理、差异化、行业洞察
- 技术架构与工程质量 15：选型、结构、可维护性、华为云服务
- 交付规范性 5：材料完整、文档可复现

输出：
1. 总分与各维度分数；
2. 每个维度的证据与扣分原因；
3. 最可能被评委追问的 5 个问题；
4. 按投入产出排序的改进清单（今天/明天/提交前）；
5. 一句话评语。
```

## 7. 提交包检查与说明

### 提示词

```text
请生成一份《提交包检查清单》和一段《提交说明.txt》模板。

要求：
1. 检查 zip 命名：作品名称+队伍名称+版本号+联系方式。
2. 检查五个目录：ppt/、project/、video/、codearts_proof/、readme/。
3. 检查 project/ 是否包含：源码、requirements、package.json、Docker、.env.example、README、tests、示例数据。
4. 检查 readme/ 是否覆盖赛题四项。
5. 检查 codearts_proof/ 是否有五类真实证据与索引。
6. 检查敏感信息：API Key、数据库密码、个人手机号、真实姓名、未授权素材。
7. 生成提交说明：在线演示地址、测试账号、启动命令、联系人、版本、已知限制。
8. 给出一段 50 字以内的“作品一句话简介”，用于提交表单。
```
