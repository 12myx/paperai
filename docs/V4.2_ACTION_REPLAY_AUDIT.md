# V4.2 Action Replay Audit

> Date: 2026-11-06
> Scope: persistent action ledger, atomic claim, replay, restart, cleanup.

## 1. Before

V4.1 actions.py kept used action IDs in a process-local dict. Consequences:

- action replay state vanished on restart;
- multiple workers did not share state;
- two confirms could both pass the in-memory check;
- no durable status or error was available.

## 2. After

New SQLAlchemy model ActionRequest in backend/app/models.py:

- id (signed action token, primary key)
- user_id
- tool_name
- args_json
- args_digest
- status: pending / executing / succeeded / failed / expired / rejected
- created_at, expires_at, confirmed_at, started_at, finished_at
- result_summary, error

New actions.py:

- create_action(db, user, tool, args) persists a pending row.
- claim_action performs a conditional UPDATE:
  WHERE id = token AND user_id = user AND tool = tool AND args_digest = digest
  AND status = pending AND expires_at > now
  SET status = executing
  A single rowcount winner is the only executor.
- finish_action writes succeeded or failed.
- expire_actions marks pending expired rows.
- reconcile_stale_actions marks old executing rows failed after a restart.
- action_status reads the durable row for the status endpoint.

The HMAC token still binds user, tool, argument digest and expiry. The database row adds durable state and atomic claim.

## 3. Lifecycle

~~~text
created pending
  -> claim -> executing
  -> tool success -> succeeded
  -> tool exception -> failed
  -> expiry cleanup -> expired
~~~

A spent token cannot be claimed again. An executing row is never retried automatically; stale executing is failed, because arbitrary external side effects may already have occurred.

## 4. Verified

- 20 concurrent TestClient confirmation requests for one action: exactly 1 HTTP 200, 19 HTTP 400; knowledge count increased exactly once.
- Tampered arguments -> 400.
- Replay of succeeded action -> 400.
- Foreign user -> 400/404.
- Expired action -> 400.
- Action created, server restarted, status still pending, then confirmation succeeded; replay after restart -> 400.
- Action status endpoint reads database row.

Tests:

- backend/tests/test_v42_actions.py (2)
- backend/tests/test_v41_agent_loop.py (guarded write/tamper/replay)
- backend/tests/test_v41_vision_security.py (foreign/expiry)

## 5. Migration and compatibility

- New table action_requests.
- SQLite local database: created by init_db / SQLAlchemy create_all.
- PostgreSQL script: backend/scripts/v42_action_requests.sql.
- No existing column changed or removed.
- Account deletion also deletes ActionRequest rows.

## 6. Limits

- Concurrent proof is thread-level on SQLite, not multi-process PostgreSQL. PostgreSQL conditional UPDATE should behave the same, but it was not run (no psql/Docker in this environment).
- Exactly-once external effects are not claimed. The guarantee is at-most-once claim plus durable status; a crash between external write and finish may require reconciliation.
- Cleanup marks expired/stale rows; it does not hard-delete history.
